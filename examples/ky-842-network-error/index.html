Wrap fetch network failures in NetworkError and stop retrying unknown errors

15 files changed +397 −47

Summary

Failed fetch calls now reject with a new NetworkError instead of the runtime's raw TypeError. #fetch wraps the error only when isRawNetworkError recognizes its message, and keeps the original error in cause.

The retry rule is also narrower. #calculateRetryDelay now retries timeouts (with retryOnTimeout), listed HTTP status codes, and NetworkError. Any other error is thrown at once, so programming bugs no longer cause retries. Both changes alter what callers catch, and the PR updates existing tests to match.

Risks

1 high · 1 medium · 1 low

  1. High

    Network failures are no longer TypeError instances

    source/core/Ky.ts:832–835

    #fetch now rethrows recognized failures as NetworkError, which extends KyError, not TypeError. Caller code that checks error instanceof TypeError, error.message === 'Failed to fetch', or error.cause.code stops matching. The PR had to change such checks in test/hooks.ts, test/headers.ts, and test/memory-leak.ts. Release this as a breaking change.

  2. Medium

    Errors from custom fetch implementations are no longer retried

    source/core/Ky.ts:490–493

    Line 491 throws every error that is not a NetworkError. #fetch creates a NetworkError only for a TypeError with a known message (line 833). A custom fetch such as node-fetch rejects with its own FetchError on ECONNREFUSED, so a GET that Ky used to retry now fails on the first attempt.

  3. Low

    isNetworkError also matches the standard DOMException named NetworkError

    source/utils/type-guards.ts:75–77

    Line 76 accepts any error whose name is NetworkError. Browsers use that name for a standard DOMException, which has no request property. Code that follows the documented example and reads error.request.url after the guard throws a TypeError for such an error.
